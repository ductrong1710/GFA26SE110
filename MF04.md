## Contract and migration

See API.md for payloads, error codes, action matrix, UTC/range conventions and compatibility. Swagger contains the new DTOs, endpoints and permission descriptions. Migration `20261113064256_CropSupportFollowUp` preserves old unknown fields as NULL, indexes new RESTRICT FKs and guards downgrade when new information/history would be lost. Only isolated test databases are migrated by the test harness; deployment still requires the normal migration step.

New routes: `assign`, `follow-ups`, `reopen`, `referrals`, `history`, `alerts`, `care-activities`, `care-activities/{activityId}/images`. Existing `claim`, `request-information`, `reply`, `recommend`, `resolve`, `crop-seasons`, `sensor-readings` remain. Season list adds farm/zone/whole-farm filters.

## Demo using three roles

1. Owner with a farm membership: create/open a season, record an inspection with optional photos, then **Report abnormal crop condition**. Confirm prefilled farm/zone/crop, enter observation time and symptoms, attach sensor channels/images, submit. Alternatively use Crop support with no season selected.
2. Admin: open the NEW report, select an active Engineer, **Assign engineer**. Alternatively an Engineer may **Accept crop report**; concurrent assignment/claim has one winner.
3. Assigned Engineer: inspect observation scope, journal images, valid/error/missing sensor data and alerts. Request additional information. Owner reloads and replies. Engineer reloads and records a human recommendation with optional evidence/site-survey suggestion.
4. Owner: select feedback type, enter care/outcome and optional images/existing activity. No new journal entry is required; completed seasons are supported.
5. Engineer: resolve with an outcome/reason. Owner submits **Report no improvement / request review**. The report remains RESOLVED and the Engineer is notified. Engineer reloads and **Reopen report with reason**. Confirm old recommendations/history remain and season status/revision are unchanged.
6. Referral: Engineer requests MF-03; Owner opens the existing incident flow in a separate tab, creates an incident, refreshes choices and links it. Wrong farm/device/zone is rejected. For video, choose MF-02; history explicitly states pending integration.
7. Conflict demo: load the same revision in two sessions, submit once, then submit the stale draft. Reload preserves text/images/selection; compare history and explicitly choose **Use latest revision for this draft** before resending.

## Dependencies

- MF-02: no verified ready-video or UAV-service request API exists in this branch. No mission ID is treated as video and MF-04 creates no flights, quotes or payments. Ready-video/service linking requires the real resource/authorization contract before integration.
- AI: outside mandatory acceptance until OD-02 explicitly approves provider, input fields and limitations. Any future AI must remain an internal engineer draft with manual fallback.
